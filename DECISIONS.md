# Decisions

These are the project decisions for Cowork Booking, D1 to D28. The project team made each one; cite it as "Project team (D8)". Every row has status Decided. None is a stakeholder clarification: the only stakeholder-clarified rule is the booking price formula (course instructor, class rules PR #14 at 25ca71e, merged as 58a1477), and D8 implements it. To change a default, keep the status Decided, add "adjusted from default: <old>" to the Decision cell, give the reason in Rationale, and add a row to "Disputes decided in M1". No default has been adjusted in M1. Where two defaults meet, or a default is silent, the reading we apply is recorded in "Disputes decided in M1", and the Rationale of each default it touches points to that row. D2 cites the seed's LOCAL_TZ as a source; D25 quotes class issue #173 exactly, with the seed's name replaced by "[The platform]". Each Rationale starts with an example on the shared data (Member A, Meeting Room A at THB 300 per hour, clock 2026-10-05 10:00 Bangkok), then cites its evidence by type: course sites by label with a verbatim quote, class rules PRs by number and SHA, seed flaws by their M0 inventory ID with "source inspected at 5a1cf3d", and last the trade-off we accept.

| D3 | Opening hours | 08:00–20:00 every day. | D4 | Blocks | Start at :00 or :30 exactly. Duration is 1–8 blocks (30 min to 4 h). The end is exclusive, so adjacent bookings are allowed. A misaligned start gives 400. A start block can be chosen for duration n only if all n blocks are inside opening hours, past the notice period, and free of slot-blocking bookings (D11). | Decided | Example: 09:00-10:30 is 3 blocks; a start at 09:15 gives 400; 10:30-11:00 right after it is allowed. Why: fixes seed flaw F1, source inspected at 5a1cf3d (templates/index.html:32-33 `datetime-local` with no step; purchase.py:14 prices any count of seconds). The exclusive end keeps the seed's half-open range, and matches class rules PR #13 (at c8a302f): "Available (touching is fine, like EX-R02)". The 8-block cap bounds the price (F9). The grid offers only starts where all n blocks are bookable, so it never offers a start that the insert will reject. Trade-off: no 15-minute or full-day bookings; a 5-hour meeting needs two bookings. |
| D5 | Notice / horizon | Start ≥ `clock.now()` + 60 min. Start date ≤ today + 30 days (Bangkok date). | Decided | Example: at 2026-10-05 10:00 the earliest start is 11:00 that day, and the latest start date is 2026-11-04. Why: fixes seed flaw F2 (`book_space` never compares the start with now, app.py:700-772), source inspected at 5a1cf3d. Both limits read `clock.now()` (D27). Trade-off: no walk-in bookings for the next hour; no bookings more than a month ahead. |
| D6 | Buffer | 0 min. A cleaning gap is an open question, not approved. | Decided | Example: Member A holds 09:00-10:30 and Member B can book 10:30-11:00 in the same room. Trade-off: no cleaning time between groups. |
| D7 | Product sold | Exclusive use of a whole room. Party size 1..capacity. Why: answers, as a project decision and not a stakeholder one, the question the course instructor left on EX-R01 (class rules main at 58a1477): "what do we sell: exclusive space, group booking or shared seats? Capacity is capped at 1,000 (Disputes decided in M1, row 3). Trade-off: one person can take the 12-seat Board Room; no seat sales. |
| D8 | Price | `agreed_price_satang = round_half_up(hourly_rate_satang × blocks / 2)` at creation, stored, never recalculated. Payment never re-prices. Whole blocks make the class's fractional-second question moot; record that. | Decided | Example: Meeting Room A at THB 300 per hour for 3 blocks: 30000 × 3 / 2 = 45000, so THB 450.00, stored at creation. A later rate change to THB 400 per hour leaves it at THB 450.00. Why: implements the only stakeholder-clarified rule (course instructor, class rules PR #14 at 25ca71e, merged as 58a1477): "for a booking not covered by a subscription, Purchase calculates its booking price using the space's hourly rate at booking creation multiplied by the booked duration, rounded to the nearest whole cent; half cents round up." D8 adds the unit (satang), the block count and storage, and (a project choice, with D10) stores the same price on plan bookings, which the clarification does not cover: it says "subscription coverage remains PAY-R01". Payment consumes the price: [contexts site] "Payments does not re-price the booking." Purchase "Owns price and coverage" [extraction site]. Whole blocks make the class's fractional-second question moot: PRC-Q01 (class rules PR #4 at 9478b3e) asks "Should fractional seconds be discarded?", and a whole number of 30-minute blocks has no fractional seconds. PRC-Q01's other parts are answered by D1 and D9 (minimum charge) and by D4 and D9 (maximum rate and duration). With whole-THB rates (D9) the half-up rounding never changes the result; we keep it so the formula matches the clarified rule. The seed's `calculate_booking_price_cents` uses the same formula (Spacey: source inspected at 5a1cf3d, purchase.py:6-15). Storing the price also fixes seed flaw A15, source inspected at 5a1cf3d (the startup backfill re-prices NULL amounts, app.py:112-117). Trade-off: a booking made before a rate change keeps its old price. |
| D9 | Rate | Whole THB per hour: 0, or 20–10,000. The per-block price is then exact, and every chargeable booking is ≥ THB 10. | Decided | Example: Focus Pod 1 at THB 20 per hour costs THB 10.00 per block, the smallest charge. The Board Room at THB 1,000 per hour costs THB 4,000.00 for 8 blocks. The top rate, THB 10,000, costs THB 40,000.00 for 8 blocks. A rate of THB 15 or THB 20.50 is refused. Why: a whole-THB rate halves to whole satang, so no block price needs rounding (D8). THB 20 is the lowest rate whose block reaches the THB 10 Payment minimum (D1). The cap bounds the stored amount and fixes the rate half of seed flaw F9 (`is_valid_price` has no upper bound, app.py:216-217), source inspected at 5a1cf3d. Rate 0 keeps free spaces possible, and D10 then skips Payment. That fixes seed flaw F16, source inspected at 5a1cf3d; a class reviewer on class rules PR #4 (review at 9478b3e): "I also ran paying the zero-amount booking with no card: 400 'card_number must be 13-19 digits', still unpaid." Trade-off: no rates between THB 1 and THB 19, and no satang in rates. |
| D10 | Coverage | `pay` / `plan` / `free`. `plan` applies when the Member's `plan_active` flag (set by the operator) is true at creation. `free` applies when the price is 0. Coverage is fixed at creation, like price. Plan and free bookings skip Payment and are confirmed at once. Turning the plan off never changes existing bookings. No plan sales in v1. | Decided | Example: Member B (plan_active true) books Meeting Room A 09:00-10:30: coverage plan, price THB 450.00 stored, confirmed at once, no payment session. Member A books the Community Table (THB 0 per hour): coverage free, confirmed at once. Member A books Meeting Room A: coverage pay, sent to Payment. If the Operator then turns Member B's plan off, Member B's booking stays plan. Why: the course keeps coverage apart from collection: [extraction site] "“Covered” is not always “money collected”." and "Payment or subscription coverage?"; the contract examples include "coverage skips collection." [extraction site]. Fixes seed flaws F6 (a free, anonymous subscription keyed by a typed name, app.py:62-67 and 1004-1025), A3 (subscribing "guest") and F16, source inspected at 5a1cf3d. The flag lives on Member, whose account data the course instructor placed in Purchase (class rules PR #10 review on bb9f346); coverage is Purchase's because Purchase "Owns price and coverage" [extraction site]. Fixing coverage at creation keeps PAY-R01 (class rules PR #1 at 0326c8c): "That booking stays unpaid (subscription is checked only at creation)". It resolves known conflict K5: SLOT-T01 (class rules PR #6 at c18b638) says "A subscriber's booking is never unpaid". Trade-off: no plan sales, plan prices or plan billing in v1; a plan is a flag the Operator sets by hand. |
| D11 | Hold | 15 min. A booking is **slot-blocking** when `status='confirmed'` OR (`status='held'` AND `hold_expires_at > :now`), where `:now` = `clock.now()` passed as a parameter. Every availability read uses this predicate. Before the insert, the stale held bookings in that space are reconciled (D13) in their own short steps; the insert then runs in one transaction. A partial EXCLUDE `WHERE status IN ('held','confirmed')` guards races; its violation gives 409 (JSON) or a flashed "slot just taken" (form). A Member has at most one slot-blocking held booking. "Continue to payment" for the same space and time resumes it; a different request is refused until that hold resolves. The Member's own lapsed holds are reconciled first. | Decided | Example: Member A presses "Continue to payment" at 2026-10-05 10:00, so hold_expires_at is 10:15. At 10:14 Member B sees 09:00-10:30 on 2026-10-07 as taken. At 10:15, if unpaid, it is free again. Why: fixes seed flaw F3 (an unpaid row blocks its slot forever; the exclusion constraint covers every row, app.py:130-135), source inspected at 5a1cf3d. Class rules PR #6 (at c18b638) asks "for how long before it is released (for example, a payment deadline)?" 15 minutes is enough to pay and to retry a decline. Passing `:now` keeps the predicate testable (D27). The partial EXCLUDE keeps the seed's btree_gist race guard but ignores expired and cancelled rows. One held booking per Member stops one Member from hoarding slots. Lazy expiry needs no background job (ADR (M2): lazy hold expiry and reconciliation). Here "held" is a stored status; the class term "Held slot" (SLOT-T02, any booking, paid or not) means something else, so the glossary names them apart. The order of booking checks and the refusal of plan and free requests during a hold are in Disputes decided in M1, row 4. The stored statuses, and Completed as a derived state that is never stored: Disputes decided in M1, row 7. Trade-off: a lapsed hold stays `held` in the table until something touches it, and each insert first spends a short reconcile step. |
| D12 | Session expiry | `expires_at = hold_expires_at − 2 min`. Payment rejects attempts at or after `expires_at`, so a session's outcome is final before its hold ends. | Decided | Example: hold_expires_at is 2026-10-05 10:15, so the payment session's expires_at is 10:13; a card attempt at 10:13 is refused. Why: every payment outcome is final 2 minutes before the hold ends, so Purchase never finds money for a slot it has already released. That is why a lost redirect needs no webhook (ADR (M2): Purchase-only callers, no webhooks). The course asks both sides to agree repeat behaviour: [extraction site] "Reuse or new attempt? Agree identity and behaviour; do not assume." What the Member sees between expires_at and hold_expires_at is in Disputes decided in M1, row 4; why the booking stays held until hold_expires_at is in Disputes decided in M1, row 8. Trade-off: the Member has 13 minutes to pay, not 15. |
| D13 | Reconciliation | Purchase reconciles every held booking that has a payment session whenever it touches it: booking page, My bookings, cancel, the pre-insert sweep, and operator Reconcile. It calls `GET /payment-sessions/{id}`. If paid, it takes the fulfilment path (D14). If unpaid and the hold has lapsed, it marks the booking `expired`. If unpaid and still inside the hold, nothing changes. HTTP calls never happen inside an open DB transaction. If Payment is unreachable, nothing changes; a request that needs the result (the conflicting insert, a cancel) gets 503 / a flashed "try again". Invariant: every paid session ends as a confirmed booking or a refund attempt. | Decided | Example: Member A pays at 10:05 and closes the tab. At 10:20 Member A opens My bookings; Purchase calls GET /payment-sessions/{id}, sees paid and confirms the booking, although the hold lapsed at 10:15. Why: only Purchase calls other services, so Purchase pulls outcomes: [extraction site] "Purchase interprets the result". Each service writes only its own store: [contexts site] "Shared references connect the models. They do not make them one shared object." No HTTP call runs inside an open transaction, so a 5-second timeout (D28) never holds a row lock. A 503 when Payment is down is safer than a guess. With D11 and D12 this fixes seed flaw F3, source inspected at 5a1cf3d. Cancelling a lapsed unpaid hold (expired, not cancelled): Disputes decided in M1, row 2. An expired session leaves the booking held until hold_expires_at: Disputes decided in M1, row 8. Trade-off: no background sweeper; a stale row waits for the next touch, and Payment downtime blocks cancels and conflicting inserts. |
| D14 | Fulfilment | For a `held` booking (even if the hold just lapsed), Purchase confirms only if the session's `booking_reference`, `amount_satang` and `currency` equal the booking's; then it issues the grant (D20). On a mismatch, in the same transaction, it sets the booking `cancelled` with reason `amount_mismatch` and records a full refund request (sent right after commit). A paid session whose booking is already `expired` gets a full refund with reason `slot_unavailable`. The check itself is covered by a Purchase unit test with a stubbed `payment_client.py`, because the real Payment cannot produce a mismatch (it answers 409 to a repeat with a different amount). | Decided | Example: the session for BK-7KQ2M9 reports paid, amount_satang 45000, THB: the booking becomes confirmed, and Purchase calls POST /grants. If a stub reports 40000 instead, the booking becomes cancelled with reason amount_mismatch, and a refund of THB 400.00 is sent after commit. Why: Purchase checks the result before it applies booking rules. [extraction site] "Purchase receives": "Matching amount + outcome" and "Then applies booking rules"; [contexts site] "Same amount and currency." Refunding a mismatch or an expired booking keeps the D13 invariant: no money is kept without a booking. Payment refuses a second session for the same booking_reference with a different amount (409), so only a stub can produce a mismatch, and the test says so. Trade-off: the mismatch path is defensive code, proven only by a unit test with a stub. |
| D15 | Member / session | Login is required to book. Email is unique and lower-cased; password ≥ 8. Sessions are absolute: 12 h from login. The cookie names are `purchase_session`, `payment_session` and `access_session`, all HttpOnly and SameSite=Lax (the CSRF mitigation, recorded in an ADR). `Secure` is set when `PUBLIC_URL` starts with `https`. `SECRET_KEY` is required (fail fast). Logout clears the cookie; replay inside the 12 h window is an accepted, documented trade-off. The operator is promoted when a Member with `OPERATOR_EMAIL` registers or logs in. | Decided | Example: Member A logs in at 2026-10-05 10:00; the session ends at 22:00, whatever Member A does. Why: account data lives on Member in Purchase, as the course instructor asked on class rules PR #10 (review on bb9f346, applied in d68631f): "change the context to the existing 'Purchase' and good to go" and "In the future can be extracted in the different context" (ADR (M2): Member in Purchase). Fixes seed flaws F10 (no expiry; deploy uses the public default SECRET_KEY, app.py:20), F13 (no CSRF tokens, no SameSite), A4 and A9 (bookings under typed names), source inspected at 5a1cf3d. The three cookie names differ because browsers do not keep cookies apart by port, and all three services share localhost in the integration stack. Every service refuses to start without SECRET_KEY and sets its own cookie's flags (PUR-R03, PMT-R19, AXS-R18). Accepted trade-offs, stated plainly. (1) Logout clears the cookie in that browser only. A copy of the cookie taken before logout keeps working until 12 h after login, because the session lives only in the signed cookie and the server keeps no list of sessions. This answers class rules PR #10 (at d68631f) "should logout end the session everywhere, so a copied cookie stops working? Should sessions expire?": sessions expire; logout everywhere is not supported. (2) SameSite=Lax replaces CSRF tokens (ADR (M2): SameSite as the CSRF mitigation). It stops cross-site form posts in current browsers, but not posts from another page on the same site, and not in old browsers that ignore SameSite. So no GET runs an action a person chooses (book, cancel, pay, log out, Retry, Reconcile, archive, plan toggle, kiosk room select or scan; PUR-R37). A GET may only run the idempotent sync of D13, D19 and D20: it moves a booking only toward an outcome that is already decided, and nothing in the request can steer it, so a cross-site GET cannot trigger anything harmful. Operator promotion is never undone automatically (Disputes decided in M1, row 5). |
| D16 | Registration enumeration | "Email already registered" at sign-up is an accepted, documented trade-off. Login keeps its uniform error. | Decided | Example: Member A registered a@example.com. A second sign-up with A@Example.com is told "Email already registered". At login, a wrong password and an unknown email get the same message. Why: this is seed flaw F11 (app.py:461-462 and 485-486), source inspected at 5a1cf3d; class rules PR #10 (at d68631f) asks of that message "which does reveal it. Is that acceptable?" Our answer is yes. Accepted trade-off, stated plainly: anyone can learn whether an email has an account by trying to register it. We accept it because a sign-up page that hides this must send a confirmation email instead, and v1 sends no email. Login keeps its uniform error (app.py:492-494), so a password guesser learns nothing there. Revisit if email confirmation is added. |
| D17 | Ownership | Purchase booking pages and actions are for the owning Member or an operator; everyone else gets 404. The Access ticket URL is a bearer link (ADR). | Decided | Example: Member B opens Member A's booking page for BK-7KQ2M9 and gets 404, the same as for a reference that does not exist; the Operator sees the page. Anyone holding Member A's ticket link sees the ticket. Why: fixes seed flaw F7 (only /bookings/mine reads the session; ids are SERIAL, app.py:39 and 52), source inspected at 5a1cf3d. Answers the EX-R04 question (class rules PR #3 at 6752b24): "is it intended that only `/bookings/mine` gates by ownership while pay/cancel/unlock/get-by-id don't check who's asking?" 404, not 403, so a stranger cannot even learn that a booking exists. An anonymous request is asked to log in (form) or gets 401 (JSON) before any lookup, so it learns nothing; D17's 404 applies to logged-in Members who are neither the owner nor an operator (Disputes decided in M1, row 1). The ticket works like an emailed cinema e-ticket: a 128-bit, view-only link with no email on it (ADR (M2): bearer ticket link). Trade-off: whoever holds the link can read the ticket code and use it at the kiosk, so forwarding the link forwards entry. |
| D18 | Cancellation policy | **Held booking:** Purchase first calls `POST /payment-sessions/{id}/expire`. If Payment is unreachable, the cancel is refused (503 / flashed "try again") and nothing changes. If Payment reports the session unpaid, the booking becomes `cancelled` (no refund). If it reports paid, Purchase confirms the booking without issuing a grant, then treats it as a confirmed-booking cancel under the rule below, so the refund never depends on whether Purchase had already seen the payment. **Confirmed booking:** the Member may cancel before start, with 100% refund if ≥ 24 h before start and 0% otherwise. An operator may cancel before end, always 100%. **Coverage:** for `plan` or `free` bookings the refund amount is always 0, no Payment call is made, and the cancel screen says "No payment was taken". Unsupported and recorded in the PRD: partial cancel, reschedule, Member cancel after start, partial refunds other than 0/100%. | Decided | Example: the standard booking starts 2026-10-07 09:00 and cost THB 450.00. Member A cancels at 2026-10-06 09:00 (exactly 24 h before) and gets THB 450.00 back. At 2026-10-06 09:01 the refund is THB 0.00. At 2026-10-07 09:00 Member A can no longer cancel. The Operator can cancel at 2026-10-07 09:30 and refunds THB 450.00. Member B's plan booking refunds THB 0.00 and shows "No payment was taken". Why: [syllabus site] "Cancellation is a small, explicitly agreed change spanning the three services, with unsupported cases recorded." Fixes seed flaw F5 (cancel hard-deletes the booking and its revenue, app.py:917-930), source inspected at 5a1cf3d. A class reviewer on class rules PR #6 (review at c18b638) linked class issue #82, "Cancelling a paid booking should leave a record". Answers Q-SLOT-4 (refund and record) and Q-SLOT-5 (who may cancel) from class rules PR #6 (at c18b638). Expiring the session first closes the pay-versus-cancel race (seed flaw A1, source inspected at 5a1cf3d) and makes the refund independent of what Purchase had seen. 100% or 0% is simple to explain and to test. A held cancel whose hold has already lapsed unpaid ends as expired, not cancelled (Disputes decided in M1, row 2). Trade-off: no partial cancel, reschedule, Member cancel after start or partial refund; a Member who pays and then cancels less than 24 h before start gets nothing back. |
| D19 | Cancel orchestration | For a confirmed booking: (1) commit `cancelled` + refund amount + reason in one transaction; (2) revoke the grant; (3) refund if the amount is > 0 and coverage is `pay`. Each outcome is stored on the booking. A failed call shows "revocation pending" or "refund pending" and is retried idempotently on the booking page or by the operator's Retry. After a stored `failed` refund, only the operator may start `attempt+1`. | Decided | Example: Member A cancels BK-7KQ2M9 at 2026-10-05 12:00. Purchase commits cancelled with a refund of THB 450.00, then revokes the grant, then asks Payment for the refund. If Access is down, the page shows "revocation pending" and "refund pending" until a retry revokes the grant; then the refund is sent. Paid with card 4000000000005126, the first refund fails; the Operator starts attempt 2, and it succeeds. Why: the course keeps the three facts apart: [contexts site] "Access is revoked. The booking and successful payment remain recorded. No automatic refund is implied." Committing first frees the slot and records the decision, even if both calls fail. Revoking before refunding stops entry before money moves: the refund is sent only after the revoke has succeeded, and until then the booking shows "refund pending" (PUR-Q10). In D19, "a failed call" means a call that stored no result (a timeout or connection error). A refund that Payment answered as failed is stored and is not pending: only the Operator's attempt+1 follows it (PUR-R33). Natural keys make retries safe: (payment_session_id, attempt) for a refund, booking_reference for a revoke. Only the Operator starts attempt+1 after a stored failure, so a person sees every refund that needed follow-up. The meaning of "a failed call" and the refund waiting for the revoke: Disputes decided in M1, row 6. Trade-off: a Member can see a pending state, and money can wait for Access to come back or for the Operator. |
| D20 | Issuance | Purchase calls `POST /grants` on confirmation, and only while the booking is `confirmed` and no cancel is in progress. If Access fails, the booking stays confirmed and the ticket shows "being prepared"; issuance is retried on the booking page. | Decided | Example: BK-7KQ2M9 is confirmed; Purchase calls POST /grants and gets a gr_ grant with ticket code H7K3-9QXA. A repeat call returns the same grant and code. If Access is down, the booking stays confirmed, and the ticket shows "being prepared" until the booking page retries. Why: the course target: [extraction site] "Issue an authorised grant." and Access "Owns grants and issuance". Fixes seed flaw F4 (a new code on every unlock, never stored, app.py:984), source inspected at 5a1cf3d, and follows the course's proposed policy: [extraction site] "Proposed policy: reuse the credential for the same valid grant." Resolves known conflict K4: PAY-R04 (class rules PR #12 at 1c8ce57) claims a stored code that the seed never had, so we use it as a proposal, never as evidence. Payment and access stay separate facts: [contexts site] "Payment success ≠ access provisioned ≠ a successful door opening." Trade-off: a paid, confirmed booking can briefly have no ticket. |
| D21 | Check-in window | `[start, end)`. No early entry while the buffer is 0; if a buffer B is approved, `valid_from = start − min(B, 15 min)`. Purchase sends `valid_from`/`valid_until`, and Access only checks them. | Decided | Example: the standard booking checks in from 2026-10-07 09:00 until just before 10:30. At 08:55 the kiosk says not_open_yet (opens 09:00); at 10:30 it says closed. Why: fixes seed flaw A2 (unlock ignores the booking time, app.py:970-985), source inspected at 5a1cf3d, and answers Q07 (class rules PR #12 at 1c8ce57): "should the access code become invalid after the booking's end time?" The lock side checks time: [contexts site] "Checks subject, door, time and revocation." We check door, time and revocation. Trade-off: no early arrival to set up the room. |
| D22 | IDs | Alphabet `23456789ABCDEFGHJKMNPQRSTVWXYZ` (no 0 O 1 I L U). Booking ref `BK-` + 6 symbols. A ticket code never starts with BK, so a booking reference with its hyphen stripped never passes as a ticket; the ticket shows the reference only as "Booking ref (not for entry)". Each prefix says which service owns the ID. Trade-off: generation retries on a collision. |

## Disputes decided in M1

The project team records here each dispute raised in the M1 reviews: what was decided, and the D# it touches. No D1-D28 Decision changes meaning; each row reads a default more precisely where two defaults meet or a default is silent.

| # | Topic | Decision | Rationale |
|---|---|---|---|
| 1 | D17: anonymous callers | D17's 404 applies to logged-in Members who are neither the owner nor an operator. An anonymous request gets the login step (form) or 401 (JSON) before any lookup, on booking pages and operator pages alike (PUR-R05, PUR-R06). | It runs before any lookup, so it reveals nothing about which references exist, and a person who is only logged out is asked to log in instead of being told "not found". |
| 2 | D13 and D18: cancelling a lapsed unpaid hold | Purchase still calls expire first (D18) and applies D13 to the answer: paid goes the D18 way (confirm without a grant, then a confirmed-booking cancel); unpaid with the hold lapsed makes the booking expired, not cancelled; unpaid inside the hold makes it cancelled (PUR-R31). | D13 lists cancel as a reconcile point and says an unpaid lapsed hold becomes expired; D18 says an unpaid session makes the booking cancelled. The hold had already ended on its own, so expired is the true outcome, and D24's bookings by status counts it that way. The expire answer is the reconcile read, so no extra call is needed. |
| 3 | D7: capacity range | A space's capacity is a whole number from 1 to 1,000 (PUR-R15). | D7 sets no maximum. The cap keeps the value inside the INTEGER column, so out-of-range input gets 400, never a 500 (seed flaw F9). |
| 4 | D11 and D12: order of booking checks and the unpayable end of a hold | A booking request runs the input checks first (400), then the one-held-booking check (409), then the slot check (409) (PUR-R39). A Member with a slot-blocking held booking is refused any different request, plan and free ones included. From expires_at to hold_expires_at the hold cannot be paid, so "Continue to payment" for it sends no session request and says that time to pay has run out and when the slot is released (PUR-R40). The booking page counts down to expires_at. | One answer per request, testable; D11's "a different request is refused" read literally; both pages show the same payment deadline. |
| 5 | D15: operator promotion | is_operator is never removed automatically when OPERATOR_EMAIL changes. Whoever registers the OPERATOR_EMAIL address first is promoted: an accepted risk while v1 has no email confirmation (PUR-R04, PUR-Q04). | D15 names only the promotion path. Register the operator account right after first start. |
| 6 | D19: "a failed call" and the order of revoke and refund | A failed call is one that stored no result (timeout or connection error). The refund is sent only after the revoke has succeeded; until then the booking shows "refund pending" (PUR-Q10, PUR-R32). A refund that Payment answered as failed is stored and is not pending; only the Operator's attempt+1 follows it (PUR-R33). | Keeps D19's order and its reason: entry stops before money moves. |
| 7 | D11 and D24: derived booking states | Purchase stores only the statuses held, confirmed, expired and cancelled. Completed (a confirmed booking whose end has passed) is derived by Purchase when it shows the booking and is never stored; no-show is derived by Access only (PUR-R28, PUR-T22, AXS-T05). D24's bookings by status counts the stored statuses, so a completed booking counts as confirmed. | Keeps one source of truth: a derived state is computed from the stored status and clock.now(), so it cannot drift. |
| 8 | D12 and D13: the last 2 minutes of a hold | Rejected: expiring the booking as soon as Payment reports the session expired. D13 stays as written: the booking stays held until hold_expires_at, then reconciliation expires it. Until then the page says that time to pay has run out (row 4, PUR-R40). | D13 expires an unpaid booking only once its hold has lapsed, and D11's slot-blocking predicate reads hold_expires_at alone, so one deadline governs the slot. Expiring at expires_at would add a second deadline and change what D13 says, and no M1 row changes a default's meaning. |
